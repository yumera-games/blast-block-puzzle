**目的はアートではなく、コアルールが面白いかをスマートフォンで検証すること。**

「ブロック配置 × LINE CLEAR × COLOR BLAST × 特殊ピース連鎖」だけを、
グレーボックス表示で最短に確かめるための実装です。

ステージ教材、報酬表示を作り直してあります（[Phase 2A で変えたこと](#phase-2a-で変えたこと)）。

（[Phase 2C で変えたこと](#phase-2c-で変えたこと)）。

## resolution の構造（ここが核）

1 回の配置につき、以下を安定するまで繰り返します。1 周が CHAIN 1 回です。

1. 完成ライン（行・列）を**確定**する。**探索中にセルを消さない**
2. 完成ライン上の通常セルを起点に COLOR BLAST を探索する（上下左右のみ）
3. 前の wave で消去に巻きこまれた特殊ピースを起爆する
4. 特殊ピースの生成位置を決める（**生成セルは消さずに残す**）
5. まとめて消去し、消去に巻きこまれた特殊を次の wave へ送る

特殊が別の特殊を巻きこむ限り wave が続きます。同じ特殊が同一 resolution 内で
二重起爆しないよう `uid` で管理し、`BALANCE.resolution.maxWaves` で無限ループを止めます。

**表示は wave 単位で追いかけます。** `place()` の時点で論理状態（スコア・目的・クリア判定）は
確定しますが、HUD は `StageState.presentation(n)` が返す「先頭 n wave まで再生した見え方」を
描きます。そうしないと CHAIN の演出が始まる前に最終スコアと達成マークが出てしまいます。
最終 wave まで進めば表示と論理状態は必ず一致します（同じ集計関数を使っているため）。

## Phase 1 で暫定的に決めたこと

仕様書で明示されていなかったため、**実装を壊さない最小の暫定値**を置いた箇所です。

| # | 決めたこと | 理由 |
| --- | --- | --- |
| 1 | **CHAIN の単位 = 消去 1 波**。CHAIN 2 以降は「特殊の起爆」で進む | このゲームには重力が無く、消去でセルが増えないため、配置以外の要因で新しい完成ラインは発生しない。実装は毎 wave でライン探索をしているので、将来重力を入れれば仕様書の例（Rocket → 新規 LINE CLEAR）もそのまま動く |
| 2 | 特殊生成は **1 wave につき最大 1 個**、優先順位 Rainbow > Bomb > Rocket | 「2 ライン同時 + 大きな BLAST」のように条件が重なったときの挙動が未定義だったため |
| 3 | Rocket の向き：完成ラインが行だけ→縦 / 列だけ→横 / 混在→生成セルの行列で埋まっている方向 | 仕様書で「暫定でよい」と指定。`pickRocketDirection()` 1 か所に閉じてある |
| 4 | Rainbow の対象色 = combo 相手の色 → 自分の色 → 今回置いた piece の色 → 盤面最多色 → COLORS 先頭 | 「resolution event から決定可能」を満たしつつ決定論にするため |
| 5 | スコアのセル倍率は **1 セルにつき 1 つだけ**（special 1.5 > blast 1.25 > line 1.0） | 倍率の積算方法が未定義だったため。CHAIN 倍率だけが上から掛かる |
| 6 | `deadRetries = 64` | 24 では「空きが 1 マスだけ」の盤面で Dead セットを配ることが実測であった。避けるのは Dead のみで Risky は出すので、救済にはならない |
| 7 | 1 ピース内の通常セルは**完全に同一色**（例外なし） | 仕様書の「原則として同一色」を最小実装した |

## Phase 2A で変えたこと

Phase 1 の実物レビュー（393x852 実機・統計測定）で出た問題への対応です。
**数値はすべて `src/data/balance.ts` に集約してあり、ロジック側へ直書きしていません。**

| # | 変更 | 理由（Phase 1 の実測） |
| --- | --- | --- |
| 1 | `colorBlast.minSize` を 4 → **5** | 全配置の 47.5%（1手あたり）で COLOR BLAST が起き、うち約半分が最小サイズ 4 だった。特別感が無い |
| 2 | COLOR BLAST サイズによる特殊生成を段階化：**5〜7 なし / 8〜10 Rocket / 11〜14 Bomb / 15+ Rainbow** | Rocket 276 < Rainbow 283 < Bomb 1585 と、**最弱の Rocket が最もレア**という逆転が起きていた |
| 3 | combo の条件を「盤面で隣接」→ **「起爆効果が実際に相手へ届いた」**。届いた相手は起爆待ちでなくても取り込む | 隣接条件では 48,000 手で combo 14 回（起爆の 0.69%）しか成立せず、combo 系の効果が事実上の死に仕様だった |
| 4 | スコア・目的・CHAIN の表示を **wave 単位**へ | 配置した瞬間に最終スコアと目的の達成マークが出てしまい、CHAIN の演出前に結末が漏れていた |
| 5 | Stage 5 / 6 / 8 / 9 / 10 を作り直し | Stage 5 は ROCKET 生成と同時にクリアして起爆を見せられず、Stage 6 はライン外が 1 マスしか増えない教材だった |

### combo の判定（Phase 2A）

起点は、消去に巻きこまれて**起爆が確定した特殊**です。
その特殊が単独で起爆したときの効果範囲が別の特殊へ届いたら、
**相手がまだ起爆待ちでなく、盤面に残っているだけでも**同じグループへ取り込み、
1 回の combo として処理します。取り込んだ相手の単独効果がさらに別の特殊へ届けば、
そのまま推移閉包を取ります（A の射線が B に届き、B の範囲が C に届くなら A・B・C で1グループ）。

- 起爆待ちどうしは、**どちらか片方が届けば**結びます（両方とも起爆するため）。
- 盤面に残っているだけの特殊は、**届かれたときにだけ**取り込みます（自分からは起爆しない）。
- Rainbow だけは効果が「対象色のセル全体」で通常セルしか含まないため、
  **対象色を持つ特殊へは届く**ものとして扱います。
- 同じ wave・同じ resolution に居るだけでは combo になりません。効果が実際に届いた場合だけです。
- 取り込んだ特殊は uid で起爆済みにするので、次の wave で再起爆しません。
- 走査はすべて index 昇順で、結果は決定論です。

なお、**グループの合成効果**が届いた先の特殊は取り込みではなく次の wave へ送られ、
通常の CHAIN として伸びます（取り込みの判定に使うのはあくまで各メンバーの単独効果）。

## Phase 2C で変えたこと

Phase 2C は**ステージ教材だけ**の変更です。コアルール（閾値・到達判定・効果範囲・
スコア倍率・盤面サイズ）には一切触れていません。

きっかけは、人間プレイ評価で Stage 10 はクリアできたのに Stage 11 が解けず、
「何を狙えばよいか分からない」「特殊の使い方が分からない」「COMBO と CHAIN の違いを
説明できない」という結果が出たことです。教材の連鎖に 3 か所の断絶がありました。

| # | 断絶 | 対応 |
| --- | --- | --- |
| 1 | ROCKET の**向きの決まり方**をどこでも説明していなかった。Stage 5 は「たて向き」を作るのにそう言わず、Stage 8 だけが「よこ向き」と結果を書いていた | Stage 5 / 8 の intro を「生成条件 → 向き → 射線」の対応が読める文章に書き直し、両方に outro（答え合わせ）を付けた |
| 2 | Stage 10 の目的が `COMBO 1回` と `CHAIN 3以上` の 2 本立てで、**1 手で両方が同時に埋まる**。区別を教えるはずのステージが区別を消していた | CHAIN objective を外し、初期盤面から 3 個目の ROCKET を外して **CHAIN 2 / COMBO 1** で終わる構成にした。intro と outro で Stage 5（CHAIN 2・COMBO なし）と明示的に比較する |
| 3 | Stage 5・8・9 が「特殊は作ったら起爆させるもの」を 3 回教えた直後、Stage 11 が案内なしでその逆（**残す**）を要求していた | Stage 11 をガイド付き教材にして「すぐ起爆させず残す」を教え、案内なしの転移確認は新しい **Stage 12** へ移した |

### ROCKET の向き（コード上の規則）

`pickRocketDirection()` 1 か所だけが決めます。ステージ側には向きを書きません。

| 同時に消えたライン | 向き |
| --- | --- |
| 行だけ（列は 0 本） | `v`（たて向き。矢印の**列**を消す） |
| 列だけ（行は 0 本） | `h`（よこ向き。矢印の**行**を消す） |
| 行と列が混在 | 生成セルの行と列で、埋まっているセルが多いほう（行が多ければ `h` / 列が多ければ `v`）。**同数なら `h`** |

8x8 では、行と列が混在するのは「行 1 本＋列 1 本」の場合だけです
（2 本以上になるとライン数 3 で Bomb 側の条件が先に立つ）。
そのとき生成セルの行も列も 8 マス埋まっているので必ず同数になり、**結果は常に `h`** です。
Stage 8 の「行と列を同時に消すと よこ向き」はこの帰結で、例外はありません。

### CHAIN と COMBO の分離

- **CHAIN** … 解決（resolution）が何波続いたか。`ResolutionResult.maxChain` = event 数。
  特殊が 1 個だけ起爆しても 2 になる。
- **COMBO** … 1 つの起爆グループに特殊が 2 個以上入ったこと。
  `detonation.group.length >= 2` で数える。

Stage 5（たて ROCKET 単独起爆）と Stage 10（ROCKET+BOMB）はどちらも CHAIN 2 ですが、
COMBO は 0 と 1 です。この 1 組が「CHAIN の数と COMBO の有無は別」の教材になっています。

### 盤面の動きで意味を見せる（Phase 2C 修正・第2版）

文章による説明は**読み流される**ことが人間再評価で分かった
（CHAIN 2 を「2列そろった」、COMBO は「取れた」としか受け取らない／intro は流し読み／
中央の説明は消えるのが早くて覚えていない／長い文章は読むのが面倒）。
そこで文章は最小限にし、意味は**ルールが起きた瞬間の盤面上の動き**で見せる。

出す教材はステージデータの `tutorial.teach` だけが決める（`src/data/resultText.ts` の `TeachKind`）。

| teach | ステージ | 見せ方 |
| --- | --- | --- |
| `waveNumbers` | 5 | wave に ① ② を振り、①→② を矢印で結ぶ。**1 wave = 番号 1 個**なので、2 ライン同時消しでも ① のまま |
| `comboLink` | 10 | いっしょに起爆した特殊を同じ枠・同じ脈動で囲み、矢印で結ぶ。消えた側は残像で位置を示す |

**矢印の向きは `Detonation.group` の配列順から取らない。** group は決定論のため index 昇順に
並べてあるだけで、因果の意味を持たない（配列順をそのまま向きに使うと矢印が逆を向く）。
向きは `comboLinkOf()` が消去記録から決める。効果を届かせた側は**前の波**でラインに
巻きこまれて消えているのでその波の `removed` に入らず、取り込まれた側は起爆範囲に
含まれて**その波**で消えるので `removed` に入る。起爆待ちどうしが結ばれた場合は
取り込まれた側が居ないので向きが定まらず、`directed: false` として
**片方向の矢印を出さず**向きのない線で結ぶ（推測した向きは表示しない）。
| `keep` | 11 | 残す特殊へ四隅のブラケットと弱い脈動。盤面上部に「[BOMB] ＋ [まだ無い特殊=点線] → COMBO」の小さな図 |

Stage 12 には一切付けない（転移確認のため）。

**読み終わるまで止める。** 教材の山場が起きた手だけ、演出の最後で止めて
「タップで つづける」を出す。**そのステージで 1 回だけ**なのでテンポは落ちず、
同じ説明を繰り返さない。止まっているかは `__blast.state().awaitingTeach` で読める。

### 意味を発生した瞬間に出す（Phase 2C 修正）

人間プレイ評価で、CHAIN と COMBO が **「ROCKET と BOMB の違い」**として受け取られていました
（「縦横一列を消すか爆発するかの違い」「列を消す、まわりをまとめて消す」）。
説明カードを増やすのではなく、**実際に起きた wave の上に意味を出す**ようにしています。

```
ROCKET + BOMB            ← 組み合わせ名
COMBO!
特殊 2個が いっしょに起爆！   ← COMBO の意味（group の実数）
                            ← ここを広く空け、板も別にする
CHAIN 2
消去が 2回 つづいた！        ← CHAIN の意味
```

出す条件も文言も `src/data/resultText.ts` の `waveNotice()` 1 か所です。
**表示側は combo を判定し直しません。** 見るのは `chainIndex` と
`Detonation.effect` / `Detonation.group` だけで、`waveNotice` は wave 単位に独立なので
COMBO 表示が次の波へ持ち越されることはありません。

### 無言の詰みを作らない

Stage 11 の旧版は、行 3 の残り 1 マスを埋めると BOMB が単独起爆し、
2 セット目には縦ピースが無いため**その時点で達成不能が確定するのに、
理由を告げないまま残り手数だけ進む**構造でした。次の 2 点で解消しています。

- **1 手では詰まない盤面**：Stage 11 の行 3 の空きは離れた 2 マス、列 3 の空きは 7 マス。
  どのピースを 1 個置いても完成しないので、1 手で BOMB を単独起爆させられない。
  Stage 12 も同様（行 5 の空き 7 マス、列 3 の空き 6 マス）。
- **回復経路**：2 セット目に 1 セット目と同じ 3 種類（v2 / h3 / h4）を入れ、手数に余裕を持たせた。
  ROCKET を作る手を無駄にしても、行を作り直して同じ形へ戻せる。

合法な 1 手目すべて（Stage 11 は 85 通り、Stage 12 は 99 通り）について、
残り手数内に COMBO へ届く手順が存在することをビーム探索で確認し、
代表的な誤操作 1 回ぶんはテストへ落としてあります。

## 既知の問題 / Phase 2B 以降への申し送り

- **重力が無いため、CHAIN は特殊の起爆でしか伸びない。** 仕様書の CHAIN の例をそのまま
  成立させたいなら、重力の有無自体が設計判断になる（Phase 2A では重力を入れていない）。
- **特殊の生成率が 4.49% → 7.35% へ増えた。** Rocket の生成閾値（BLAST 8）が
  現実的に届きやすいため。強さの順序は正しくなったが、総量は Phase 2B で見直す余地がある。
- **combo が増えたぶん、CHAIN は短くなった（CHAIN 3 以上が 0.21% → 0.13%）。**
  以前は「Rocket 起爆 → 次の wave で Bomb」と 2 波に分かれていた因果が、
  効果到達 combo では 1 波にまとまるため。combo 成立は 0.69% → 17.37% へ増えている。
  派手さを wave 数で出すのか 1 回の combo 規模で出すのかは Phase 2B の判断。
- Rainbow が盤面に残ったまま対象色が 1 つも無くなると、起爆しても自分のマスしか消えない。
- 演出は最低限（ライン強調・縮小フェード・起爆範囲のフラッシュ・CHAIN 文字）。
  Rocket / Bomb の方向や範囲は「範囲を塗る」だけで、飛翔体などは無い。
- Stage 4〜12 の想定解は固定 piece 列の中で完結する。固定列を使い切った後は
  seed 乱数になるため、別解を試すと候補が変わる。
- **CHAIN / COMBO の用語理解と「BOMB を意識的に残す戦略」は、人間評価でまだ未達。**
  Stage 12 は RETRY で 3 手クリアでき、ROCKET の向きは「縦向き。横を揃えたから」と
  説明できた一方、CHAIN と COMBO の意味は「分からない」、BOMB を残すことは
  「特に考えていなかった」という回答だった。意味表示（上記）はその対策で、効果は未検証。
- **Stage 1〜4 が単調**（4 ステージ・8 手かけて新しい情報は「ラインはたてでも消える」1 つだけ、
  Stage 2 と 4 は intro も無い）。Phase 2C は Stage 5 以降の教材連鎖の修正が目的なので、
  ここは手を付けていない。導入の圧縮は次フェーズの検討事項。
- **初見発見可能性は未検証。** Phase 2C の文言・ステージ構成が実際に初見のプレイヤーへ
  届くかどうかは、人間プレイ評価をやり直すまで分からない。自動プレイで確認できるのは
  「実装が想定どおり動くこと」だけ。

## 検証

```bash
npm run test    # コアロジック 186 ケース（ブラウザ不要）
npm run smoke   # 320/375/393/430 px での表示 + 実ドラッグでの Stage 1〜12 通しプレイ
npm run stats   # 発生率・combo 率・生存手数の測定（前後比較に使う）
```

`npm run smoke` は、objective 行が**横に省略されない**（`scrollWidth <= clientWidth`）ことと、
**ゲーム領域と縦に重ならない**（交差長 0）ことを Stage 1〜12 x 4 幅で実測します。
canvas の寸法は `#stage-wrap` の実寸から決まり、その高さは目的の本数と
ヒント行の折り返しで変わります。作り直さないと canvas が `#stage-wrap` をはみ出し、
`overflow: visible` + `align-items: center` なので objective 行の上へ重なります
（DOM 順で canvas のほうが後ろなので、上に描かれて文字が読めなくなる）。
`main.ts` の `fitToAvailableSpace()` が表示領域の変化を見て作り直します。

`tests/stages.test.ts` は Stage 1〜12 の**想定解**を持っていて、
目的が実際に達成できることを毎回確かめます。ここが落ちたら、
ステージデータかコアルールのどちらかが壊れています。
