## 1. 結論

### 3 案の違い（1 行ずつ）

| 案 | 一言 | 図と地の分け方 | 通常時の情報量 | 演出の伸びしろ |
| --- | --- | --- | --- | --- |
| **A：Bright Toy Pop** | 明るい地に、太い暗輪郭の立体ブロック | **輪郭**（面の輝度は地をまたぐ） | 多め（面がすべて明るい） | 中（明るい地では発光が乗りにくい） |
| **B：Candy Neon** | 暗い地に、高彩度の発光ブロック | **面の輝度差** | 中 | **大**（暗い地で光が最も効く） |
| **C：Clean Arcade** | 暗い中間地に、平面で彩度を抑えたブロック | **面の輝度差** | **少** | 中〜大（通常時は光らせず、演出時だけ増やす） |

### 推奨

**C：Clean Arcade を推奨する。ただしこれは採用決定ではない。**

**推奨理由**

1. 監査の最重要課題は「装飾が足りない」ではなく **「盤面へ集中している間に、周辺の意味表示が知覚されない」**
   （[監査 A-07 / D-01、仮説 H1・H8](../audits/MAIN_PLAY_UI_AUDIT.md#8-phase-2c-未達の原因仮説)）。
   通常時の視覚的な騒がしさが最も少ない C は、**演出が出た瞬間の差分**を最大化できる。
2. 方針文書が守るべきとした Block Blast 由来の長所（盤面の明快さ・入力の直感性・
   置ける／置けないの判断しやすさ）を、追加の工夫なしで最も素直に満たす。
3. 長時間プレイと小画面に強い。実測でも C は 320px で最も破綻が少なく、
   低彩度なので長時間の視覚疲労が小さいと期待できる（**疲労は未検証**）。
4. B が持つ「発光で派手にする」余地は、C でも **演出時にだけ**取り込める（`glow: event-only`）。
   逆に A / B の通常時の強い表現は、あとから引き算するのが難しい。

**推奨案（C）の弱点**

- **第一印象が地味。** 「ゲームを始めたくなるか」という観点では A / B に劣る可能性が高い（未検証）。
- 低彩度ゆえ、**特殊ブロックの「特別感」を色だけで出しにくい**。形と明るさに依存する。
- 現行のダーク基調と見た目が近いため、**「変わった感」が伝わりにくい**。
  人間評価で「前と同じに見える」と受け取られるリスクがある。
- 報酬の段階差を演出だけで作るため、**VFX 実装の負荷が 3 案で最も高い**（通常時に貯金がない）。

**採用前に人間が判断すべき項目**

1. 明るい画面（A）と暗い画面（B / C）のどちらを製品の基調にするか。**これは戻しにくい決定である。**
2. 「始めたくなる第一印象」と「長時間の読みやすさ」のどちらを優先するか。
3. ブロック 5 色に**形（◆●▲■✚）を常時付ける**ことを受け入れるか（下記 4-4 の理由による）。
4. 320×568 で操作ボタンの高さが 37px になることを受け入れるか、盤面を削って 44px を確保するか（6-4）。
5. 開発用 DBG を製品ビルドから完全に外すか、開発ビルド限定で残すか（12）。

## 3. 共通デザイン原則（3 案共通・変更不能案）

**3 案のどれを選んでも変わらない土台。** 変更するときは、実装より先にこの節を更新して承認を得る。

| ID | 原則 | 測定方法（第 3 段階の受け入れ条件に接続） |
| --- | --- | --- |
| **R01** | **同一 viewport では、ステージ内容によって盤面寸法を変えない。** objective の本数・ヒントの有無・教材の有無に依存させない | 全ステージで cell 値が一定かを Playwright で実測（二値） |
| **R02** | **1 つの色へ複数の重要意味を割り当てない。** 盤面レイヤーと UI クロームで名前空間を分け、同一レイヤー内での意味の重複を禁止する | 色 → 意味の対応表が 1 対 1 か（レビュー）＋ 4 節の識別条件を満たすか（計算） |
| **R03** | **色だけで状態を伝えない。** ブロック・特殊・予告・エラーは、色に加えて形・模様・動きのいずれかを必ず持つ | 各要素が色以外の手がかりを 1 つ以上持つか（レビュー）＋ 色覚差シミュレーション |
| **R04** | **通常状態と報酬演出のコントラストを確保する。** 通常時に強い表現を使い切らない | 9 節の Level 0〜5 が量として区別できるか（連続フレーム＋人間評価） |
| **R05** | **盤面が常に第一視認対象。** 盤面と、その直上の演出領域を合わせて画面高の 50% 以上を占める | `(board + event stage) / viewport 高` を実測 |
| **R06** | **1 概念 1 か所。** 同じ概念（CHAIN / COMBO / objective）を 2 か所に出さない。同時に強調する主要情報は 1 つまで | フレーム単位のサンプリングで、同概念の同時表示と矛盾を検出（監査 A-01 と同じ方法） |
| **R07** | **HUD と盤面の確定タイミングを同期する。** 表示は単一の presentation から引き、報酬の確定は説明の提示より後に置く | 10 節のタイムラインどおりの順序かをフレーム単位で実測 |

## 4. セマンティックカラー案

### 4-1. 測定方法

- コントラスト比：sRGB 値を線形化し、相対輝度 `L = 0.2126R + 0.7152G + 0.0722B` から
  `(L明 + 0.05) / (L暗 + 0.05)` を計算した。
- 色差：sRGB → CIE XYZ（D65）→ CIE Lab に変換し、**CIE76 の ΔE** を計算した。
- 色覚差：**Viénot / Brettel–Mollon (1999) の LMS 投影**を線形 RGB 上に適用して 1 型（protan）・
  2 型（deutan）・3 型（tritan）をシミュレーションした。**近似であり、実際の見え方の確認は人間評価が必要。**
- すべて `/tmp` のスクリプトで計算し、**同じ値からモック画像を生成している**ので、
  下表の色コードと画像の色は一致する。

### 4-2. 基準（ゲーム要素へ規格を機械的に適用しない）

### 5-1. 書体

**外部フォントを新規依存として追加しない。** 端末内蔵の書体スタックのみで組む。

```
--font-ui: system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP",
           "Yu Gothic UI", "Meiryo", sans-serif;
--font-num: system-ui, -apple-system, "SF Pro Display", "Helvetica Neue", sans-serif;
```

- 現行の `ui-monospace, SFMono-Regular, Menlo, Consolas, "Noto Sans JP", monospace` は、
  **欧文が等幅・和文が端末依存**という混在を生んでいた（[監査 E-01](../audits/MAIN_PLAY_UI_AUDIT.md#4-5-文字と文章e)）。
  和文を先頭に含む sans-serif スタックへ変える。
- 数値（SCORE / MOVES / CHAIN）は `font-variant-numeric: tabular-nums` を付け、桁揺れを止める。
- **候補として提案するが未検証**：将来 Web フォント（例：可変ウェイトの和文ゴシック）を検討する場合、
  **ライセンス・配信方法・容量はいずれも未検証**である。本案には含めない。

### 5-3. STAGE 名の省略問題（監査 A-04）への解

現状は **48 通り中 47 通りで `…` に切り捨てられている**。原因は、
ステージ名を HUD の 1 セル（幅 73〜128px、`nowrap` + `ellipsis`）に押し込んでいたこと。

**本案の解（3 案共通）**

1. **ステージ名を HUD カードから外し、画面最上部の専用行に置く。** 幅は画面の全幅を使える。
2. 行の構成は `[STAGE 10] ステージ名` の 2 要素。番号はチップ、名前は残り全幅。
3. **`text-overflow: ellipsis` を使わない。** `-webkit-line-clamp: 2` で 2 行まで折り返す。
4. **2 行に収まらないステージ名はデータ側を短くする**（表示側で黙って切らない）。
   これは `stages.ts` の変更を伴うため、第 3 段階の実装対象とする（本資料では変更しない）。

**実測（モックでの検証）**：現行で最長の `11. 特殊を 残して COMBO を 作る`（220px 必要）を含め、
320 / 375 / 393 / 430px の 4 幅すべてで**欠けなし**（`scrollHeight <= clientHeight`）。

### 5-4. ヒントと objective の大小逆転（監査 A-08）への解

現行はヒント 14px > objective 12px だった。本案では
**objective（恒常）0.26c > event stage の一時メッセージ（0.30c）** …ではなく、
**役割で分ける**：objective は「常に読める大きさ・低い彩度」、event stage は
「一瞬だけ強い・大きい」。**同時に強い状態にはしない**（R06）。
event stage が強調表示になるのは Level 2 以上の演出中だけで、通常時は `caption` 相当の弱さで置く。

```
 スロット間の間隔（7 か所）  各 0.12   各 0.15

cell = floor( min( (W - 外周余白*2) / 8,
                   (H - 外周余白*2) / (スロット比の合計 + 8 + 間隔の合計) ) )

余り = H - 使用高
  1) tray  へ  min(余り, 0.60c)
  2) event stage へ  min(残り, 0.25c)
  3) breathing（controls の下）へ  min(残り, 1.10c)
  4) なお残れば上部余白へ
```

**この式は objective の本数・ヒントの有無・教材の有無を参照しない。** これが R01 の実装形である。

4. safe-area（ノッチ・ホームインジケータ）の実値は**実機で未検証**。

## 8. 入力フィードバック（イベント契約）

**SE と haptic はまだ実装しない。** ここで定義するのは「どのイベントに何を割り当てるか」の契約である。

| **drag** | ピースが指の 1.15 セル上、着地セルにゴースト | 追従（毎フレーム） | なし | なし | 継続 | なし | 同じ |

Phase 2C の教訓（表示を足しても解決しない）に従い、**表示の総量は増やしていない**

## 15. 推奨案

### 推奨：C：Clean Arcade

**推奨理由**

1. **監査の最重要課題に最も直接効く。** 未達の中心は「盤面へ集中している間、周辺の意味表示が知覚されない」
   （仮説 H1・H8）。通常時の視覚的な騒がしさが最も少ない C は、演出が出た瞬間の**差分**を最大化できる。
2. **方針文書が守るべきとした Block Blast 由来の長所**（盤面の明快さ・入力の直感性・
   置ける／置けないの判断しやすさ）を、追加の工夫なしで満たす。測定でも盤面の階層が最も安定している。
3. **小画面と長時間プレイに最も強い**（長時間の疲労は未検証）。
4. **実装負荷が最も低い**ため、第 3 段階の予算を「見た目」ではなく
   **入力フィードバック・タイムライン・演出の段階差**（＝監査の P0/P1 の中身）へ回せる。

**捨てる案の長所**

| 案 | 失うもの |
| --- | --- |
| **A：Bright Toy Pop** | **第一印象の親しみやすさ**と、Gray Box からの「変わった感」。明るい地は「始めたくなる」感覚に効く可能性が高い。**輪郭で図と地を分ける**方式は、ブロックを明るく保てるという独自の長所を持つ |
| **B：Candy Neon** | **特殊と COMBO の派手さ**。測定でも特殊の面/空セルが 9.38 と最も強く、発光を足す余地が最大。報酬感を出しやすい |

**推奨案（C）へ取り込む要素**

1. **B から**：Level 2 以上での**発光の使い方**（`glow: event-only`）。特殊生起・起爆・COMBO のときだけ、
   B と同等の強さの発光を使う。通常時は使わない。
2. **B から**：特殊の面を**盤面で最も明るい面**に固定する規則（C も既に採用済み。比 9.41）。
3. **A から**：**トレイのピースを盤面セルの 86% で描く**規則（3 案共通で採用済み）と、
   ブロックの**固有の形**を面の中で読みやすく置く配置。
4. **A から**：勝利演出の**暖色寄りの光**（C の低彩度な基調に対して、報酬だけ色温度を上げる）。

**最大のリスク**

**「前と同じに見える」と評価されること。**
C は現行のダーク基調と骨格が近いため、人間評価で「何が変わったのか分からない」と受け取られる可能性がある。
実際の改善（レイアウト規則・色の役割整理・タイムライン）は**静止画では見えない**部分に集中しており、
Phase 2C と同じ失敗（実装は完了したが伝わらない）を繰り返す危険がある。

**緩和案**：2B での提示時に、静止画だけでなく **1 手ぶんの連続フレーム**を必ず並べる
（方針文書 第 8 節「静止画だけでは判断できない演出は連続フレームまたは画面録画も提出する」）。

### 22-1. 通常ブロック 5 色

**暗 → 明の順序と形の割り当ては A / B / C と共通・固定。** 変えたのは彩度と質感だけ。

【通常ブロック 5 色】

| ブロック | 中央の彫り込み | A2-L | L | 縁（黒ではない） | A2-H | L | 縁 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| purple | ◆ | `#6c2794` | 0.068 | `#2e1d4d` | `#7116a5` | 0.068 | `#2e1d4d` |

| green | ■ | `#28b75d` | 0.351 | `#235f52` | `#10b94e` | 0.354 | `#235f52` |

**記号を「ゲームルール上の意味」と誤解させない見せ方**

A では記号を**セル左上の高コントラストなバッジ**として置いていた。
バッジは UI の世界では「状態を示す印」であり、**ルール上の意味（例：この駒は特別）を持つと読まれうる。**

A2 では次のように変えた。

1. **位置を中央へ移す。** 角＝バッジ、中央＝模様、という読みの慣習を利用する。
2. **面に彫り込む。** 濃い影（面の輝度の 20%）と、1 セルの 1.2% だけ上へずらした白いハイライトを重ね、
   **同じ形が凹んで見える**ようにする。加算される情報ではなく、**材質そのもの**として読ませる。
3. **コントラストを抑える。** 実測で面に対し **1.34〜1.78**（A のバッジは面に対し 4 以上）。

**これは意図的な引き換えである。** 誤読は減るが、色覚差での識別しやすさは A より弱くなる。
**35px セルで彫り込みが読めるかどうかは静止画では判定できず、人間評価が必要**（27 節）。

## 25. 推奨する A2 案

### 推奨：**A2-H：Luminous Future**。ただしこれは採用決定ではない。

**推奨理由**

1. **今回の要望に直接答えている。** 「もう少し全体的に未来的」に対し、A2-L は A からの変化が小さい。
   A2-H はエッジライト・半透明ガラス・ホログラム調のグラデーション・スペキュラで、
   **静止画でも未来感の差が出ている**（`a2-comparison.webp` の 1 枚目と 2 枚目）。
2. **可読性を落としていない。** A2-L と A2-H は**骨格・レイアウト・ブロックのはしごが完全に同一**で、
   測定値もほぼ一致する（ブロック/空セル 1.38 vs 1.37、text primary 14.05 vs 14.06）。
   未来感は**素材と光**で出しており、情報を足していない（F9）。
3. **人間評価で A が最良だった 4 軸を維持している。** 明るさ・盤面可読性・空きマスの認識・
   特殊の発見しやすさは、測定上 A 以上（特にブロック/空セルは 1.06 → 1.37）。
4. **特殊と COMBO の期待感が高い。** 通常時の弱いハロー（0.22）が「これは特別なものだ」を静かに示し、
   演出時は発光を 1.00 まで上げられる。26 節の遮蔽率の段差もこの案の色で測っている。

**推奨案（A2-H）の弱点**

- **長時間プレイでの疲労が未検証。** 斜めのスペキュラとソケットの目盛りは、A2-L には無い視覚要素である。
  人間評価では「長時間遊ぶ場合：A」が挙がっており、**A2-H はその軸で A2-L に劣る可能性がある。**
- **盤面が少し賑やかになる。** スペキュラは各セルに斜めの帯を足す。
  35px セル（320px 端末）でこれが邪魔にならないかは**静止画では判定できない**。
- **中央の彫り込みのコントラストが 1.41** と、A の角バッジ（4 以上）より弱い。
  色覚差での識別を形に頼る設計なので、**読めなければ前提が崩れる。**
- **「未来的」の解釈が合っている保証がない。** 要望は 1 文であり、
  期待されているのが「ガラスと光」なのか「幾何学と余白」なのかは確認できていない。

**緩和案（2B で選べる）**：A2-H の**通常時の素材表現だけ**を A2-L 相当に下げられる。
具体的には (1) 斜めのスペキュラを 12% → 0、(2) ソケットの目盛りを消す、(3) 通常時のハローを 0.22 → 0.10。
**配色・骨格・レイアウトは変わらない**ので、この 3 つは独立に調整できる。

### 25-1. A2-L を選ぶべき場合

次のいずれかが人間評価で確認された場合、**A2-L が正しい選択になる。**

- 320px の実機で A2-H のスペキュラが盤面を読みにくくする。
- 20 分以上の連続プレイで A2-H が疲れる。
- 「未来的」の期待が「光沢」ではなく「簡素さ」だった。

## 26. 気持ちよさについて（未判定）

**人間評価の「気持ちよさ：静止画では判断不能。実際の光・消去・COMBO 演出次第」を、そのまま引き継ぐ。**

- 本資料の 24 節は**光量・方向・時間・強度の設計案**であり、**気持ちよさの評価ではない。**
- 遮蔽率が単調に増加していることは「強度の段差が量として存在する」ことしか示さない。
  **段差が気持ちよさとして感じられるかは測定していない。**
- 音・振動は未実装のため、**演出の半分が欠けた状態**での判断になる。
- gray-box の形（矩形の帯・円のリング）は暫定であり、完成 VFX の印象とは異なる。

**したがって、A2-L / A2-H のどちらが気持ちよいかは、本資料では判定していない。**
これは第 3 段階で実際に動かしてからでないと決められない（27 節）。

## 27. 第 3 段階で実演しないと判断できない項目

## 32. A2-HW の設計意図とグラデーション規則

### 32-1. ねらい

### 32-2. 「青く塗り替えるだけ」「ベージュへ戻すだけ」にしない構造

**暖色を面の基調色にはしない。暖色は「光」としてだけ入れる。**

### 32-6. 特殊ブロック

- **本体は白／シルバー `#eff1f2`**（盤面で最も明るい面）。**通常時の縁は淡いシアン `#04425c`。**
- **種類の区別は形が最優先。** ROCKET＝カプセル＋軸方向の二重シェブロン、BOMB＝円＋放射状のスパイク、
  COLOR BLAST＝同色の塊を囲む衝撃波リング。**発光だけで種類を区別しない。**
- **起動時のみ** `G-SPECIAL-FIRE`（シアン → 紫 → 暖色）が射線／範囲に沿って流れる。
  通常時はこのグラデーションを使わない。

## 33. 冷たさを避けるために実際に行ったこと（8 手段）

要求された 8 項目すべてについて、何をしたかと実測を記す。

| # | 手段 | A2-H | **A2-HW** | 実測 |
| --- | --- | --- | --- | --- |
| 1 | **背景の暖色環境光** | なし | `G-BG-WARM`：右下から淡いピーチ `#fddcc6`、中心 42% → 56% で 14% → 0% | 背景の最も暖かい実描画画素 `#fdeadd`（Lab b\* = 8.6） |
| 2 | **surface の微弱な暖色反射** | なし | `G-SURF-WARM`：objective と feedback の右上のみ、30% → 0% | 実描画で objective の暖色側の下地が `#efe4f4` 系まで転ぶ |
| 3 | **角丸の硬さ** | cell の 11% | **cell の 11%（据え置き）** | 精密さは崩さず、柔らかさは光で出す方針 |
| 4 | **影の色** | 青寄りの灰（`rgba(30,42,70,…)`） | **暖色寄り（`rgba(52,44,40,…)` / `rgba(60,50,44,…)`）** | 影の色相が青 → 中間へ |
| 5 | **白の色温度** | 青寄りの白 `#f6f7fb` | **わずかに暖かい白＋背景側で暖色に転ぶ** | 画面地の輝度 0.858 → **0.901（+5.0%）** |
| 6 | **文字色を純黒でなく温度のある濃紺／チャコールに** | `#1c2542`（青寄り濃紺、C\* 20.5） | **`#312925`（温度のあるチャコール、C\* 4.9）** | 純黒 `#000` は使っていない |
| 7 | **勝利・達成時の暖色光** | なし | `G-VICTORY`（淡いシャンパン `#fcf1db` → 濃い金 `#c88808`）、**CHAIN を暖かい金へ移した** | CHAIN `#056978`（シアン） → **`#a97807`（金）** |
| 8 | **ピースの弾力・柔らかい動き** | — | 8 節の入力フィードバックを継承（pickup 1.08 倍 60ms、drop 0.92→1.00 スナップ 90ms）。**A2-HW ではさらに、起動時の光が暖色で終わる**（34 節） | モーションシートの ROCKET 起爆で射線の先端が暖色 |

### 33-1. 禁止事項を守っていることの確認

| 禁止 | 確認方法 | 結果 |
| --- | --- | --- |
| 全体をベージュへ戻す | 面の基調色に暖色を使っていない。暖色は環境光・反射・報酬のみ | 画面地の基調は `#f5f6fd`（クールホワイト） |
| 木・紙・布の質感 | テクスチャを一切使っていない（純粋な色とグラデーションのみ） | — |
| レトロ玩具感 | 太い暗輪郭・厚いベベルを使っていない（縁は cell の 3.2%） | A の 8.5% に対し 38% の太さ |
| 過剰な虹色グラデーション | 1 要素に載るグラデーションは最大 2 枚。stop は 2〜4 個 | 32-3 の表 |
| 全要素の常時発光 | 常時発光するのは**特殊の淡いハローだけ**（不透明度 0.20） | 通常時の盤面遮蔽率 **0.6〜0.7%** |
| 背景とブロックの色が混ざる | ブロック面に暖色光を重ねていない。ブロック / 隣のソケットの実測最小 **2.36** | 34-2 |
| 光沢で盤面が騒がしくなる | 盤面のエッジ量が A2-H より**減っている**（4.26 → 3.89） | 34-2 |
| 既存 UI の模倣 | 具体的な製品の画面・素材・配色を参照していない。すべて色コードから構成した | — |

### 34-4. 常時画面が A2-H より騒がしくなっていないか

| 指標 | A2-H | **A2-HW** | 判定 |
| --- | --- | --- | --- |

## 37. 未検証事項

**数値で「冷たくない」と断定していない。** 以下はすべて人間確認が必要である。

| # | 未検証 | なぜ数値で決まらないか |
| --- | --- | --- |
| 1 | **「冷たくない」と感じるか** | 色温度・彩度・輝度の測定値は「暖色が存在すること」しか示さない。**印象は測っていない** |
| 2 | **グラデーションが「効いている」と感じるか** | 不透明度 42% / 30% / 22% という数値は、感じ取れる強さの保証にならない |
| 3 | **明るさが「ちょうどよい」か** | 画面地 L 0.901 は A2-H より 5% 明るいが、明るすぎる可能性がある（屋内・屋外で異なる） |
| 4 | **未来感が保たれているか** | 暖色を足したことで「未来的」が薄まった可能性がある。W1 と W4 は相反しうる |
| 5 | **長時間プレイでの疲労** | 明るい画面は長時間で疲れる可能性がある。20 分以上の連続プレイが必要 |
| 6 | **中央の彫り込みが 35px セルで読めるか** | 第 2 ラウンドから未解決（27 節の項目 4） |
| 7 | **COMBO の暖色合流が「気持ちよい」か** | gray-box であり、音・振動・粒子の形は未実装。**気持ちよさは静止画・コマ送りからは未判定**（26 節） |
| 8 | **実機での色再現** | 有機 EL のガンマ・色域で、淡い暖色環境光（Lab b\* = 8.6）が沈む／転ぶ可能性 |
| 9 | **屋外・低輝度環境での可読性** | 明るい画面は屋外で有利、暗所で眩しい可能性 |
| 10 | **320px で操作ボタン 37px を許容するか** | 6-4 の判断項目 3。第 3 ラウンドでも未解決 |
