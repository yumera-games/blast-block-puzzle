## 2. 監査範囲と方法

### 対象

メインプレイ画面と、それに直接付随する状態のみ。メニュー・ショップ・図鑑・設定は対象外。

| 区分 | 実際に描画・計測した状態 |
| --- | --- |
| 通常 | Stage 1 / 4 / 6 / 7 / 12 |
| 特殊・報酬 | Stage 5（ROCKET・CHAIN 2・教材停止）/ 8（ROCKET の向き）/ 9（BOMB）/ 10（COMBO・教材停止）/ 11（KEEP） |
| 入力 | ドラッグ中の通常予告 / COMBO 予告 / 合法配置 / 不正配置 |
| 終了・操作 | STAGE CLEAR / FAILED / RETRY / STAGE SELECT / DBG 開閉 / モーダル表示中 / 教材の一時停止中 |

### 環境

| 項目 | 値 |
| --- | --- |
| ブラウザ | Chromium（Playwright 同梱、`/opt/pw-browsers/chromium`）、ヘッドレス |
| 配信 | `npm run build` した `dist/` を静的配信（`http://localhost:5183/`） |
| viewport / DPR | 320×568 @2 ／ 375×667 @2 ／ **393×852 @3** ／ **430×932 @3** |
| 入力 | `page.mouse` によるドラッグ（`pointerdown → pointermove → pointerup`）。タッチ経路は既存の `tools/smoke.mjs` が別途確認済み |
| 計測 | `requestAnimationFrame` によるフレーム単位のサンプリングと `performance.now()`。**アプリ側へ計測コードは追加していない**（一時スクリプトは `/tmp` に置き、コミットしていない） |

DPR は実スマートフォン相当を含む。320/375 は DPR 2（iPhone SE 系相当）、393/430 は DPR 3（近年の 6 インチ級相当）で描画した。

### 自動確認と人間評価の区別

方針文書 第 8 節に従い、次を厳密に分けている。

- **本監査で確定できるのは「実装が何をどう描画・反応しているか」だけ**である。
- **クリアできたこと・自動テストが通ったこと・Playwright が正解手順を実行できたこと・
  教材表示が canvas 上に存在したことを、理解や満足の証拠として扱っていない。**
- 「気づくか」「分かるか」「気持ちよいか」は本監査では判定していない。
  該当箇所は第 4 節の「確認区分」列で **人間確認** と明示した。

### 未測定（推測していない項目）

- 実機での**タッチから発光までの総遅延**（パネル・コンポジタ・OS の入力処理を含む）。本監査で得たのは
  ブラウザ内部のイベント受信からフレーム更新までの値のみ。
- 実機でのフレームレート・フレーム落ち。ヘッドレス Chromium では rAF 間隔が一貫して 16.7ms だった。
- 指・手による盤面の遮蔽量。実機で実際に持って操作しないと測れない。
- 実機の色再現（有機 EL のガンマ・色域）。コントラスト比は sRGB 値からの計算値。
- 環境音・イヤホン有無の影響（そもそも音が未実装のため評価対象にならない）。
- **初見プレイヤーの理解・注意配分**。第 8 節の仮説はすべて未検証。
- iOS Safari / Android Chrome の実機挙動（safe-area、`env()` の実値、100vh 問題）。

### 規格について

コントラスト比・寸法は**測定値をそのまま記載する**。
特定のアクセシビリティ規格への適合・不適合は**判定していない**（第 11 節参照）。

### ベンチマークの扱い

Toon Blast / Block Blast の実物を本監査で確認していない。
本文中の比較はすべて **[開発方針](../DEVELOPMENT_POLICY.md) 第 2 節で定義された品質軸との比較**であり、
実際の画面・素材・配色・アイコンを参照したものではない。複製の提案も行っていない。

### 証拠画像

すべて**実際のアプリを実ブラウザで描画したスクリーンショット**。画像生成によるモックは使っていない。
加工は「切り出し・縮小・並べてラベルを付ける」ことのみで、描画内容は変更していない。

## 4. 問題一覧

**重要度**：P0 操作不能・進行不能／P1 主要理解・入力・製品品質を大きく損なう／P2 明確な品質低下／P3 改善候補
**確信度**：高＝実測値または実装コードで確定／中＝実測から強く推定／低＝仮説
**確認区分**：自動＝本監査で確定済み／人間＝人間評価が必要

### 7-2. 測定限界（**未測定**）

- **実機のタッチ → 発光までの総遅延。** 本測定はブラウザ内部のイベント受信からフレーム更新まで。
  タッチパネルのサンプリング、OS の入力処理、コンポジタ、ディスプレイのリフレッシュは含まない。
- **実機のフレームレートとフレーム落ち。** ヘッドレス Chromium では 60fps 一定だったが、実機では未検証。
- **セル移動 → 予告更新の正確な値。** 同一フレーム内で完結するため、rAF の粒度（16.7ms）より細かくは測れない。
  コードに計測を追加すれば測れるが、制約により追加していない。
- 実機のタッチのつかみやすさ（ドラッグ開始の判定・誤タップ率）。

### 7-3. 所見

- **入力から画面が変わるまでは速い**（すべて 1 フレーム以内）。方針文書 第 2 節の品質軸「操作への反応」のうち、
  **反応の速さは現時点で問題になっていない。**
- 問題は速さではなく、**反応の内容**（C-01：不正配置に見える反応が無い）と、
  **反応が終わった後の時間の使い方**（D-01：静止画で待たせる）にある。

| **H8** | **視線の移動が大きすぎる。** 関連情報が画面高の 92.5% に散っており、盤面を注視している間、上下端は視野の外にある | 実測（第 6-1 節） | 盤面の近くへ集約した版での比較 |
| **H9** | **語が盤面現象と対応していない。** 「CHAIN＝消去の波数」は盤面上に数えられる対象が無い。数えられるのは消えた行の数の方で、人間評価はまさにそう誤認した | 人間評価第 3 節 | 波を数えられる形（例：波ごとに間を空ける・波ごとに色を変える）にした版での比較 |
| **H10** | **教材が操作の目的と競合している。** プレイヤーの目的は objective の達成で、教材はそれとは別の情報として出てくる | objective は最上部、教材は盤面中央、と面が別（**A-06**） | 目的そのものを教材にした設計（例：objective に COMBO を要求し、その達成過程で意味が現れる）との比較 |

**共通する構造**：Phase 2C は「文章が読まれない → 動きで見せる」と対処したが、
本監査の実測では **動き自体が（1）小さく（2）短く（3）他の表示と同時で（4）読ませる時間帯には止まっている**。
**同じ層に表示をさらに足しても解決しない可能性が高い**という Phase 2C の申し送りは、
本監査の実測とも整合する。

## 9. 第 2 段階で定義すべきデザインシステム項目

**ここではデザインシステムを作らない。** 本監査から導かれる「定義すべき項目」を優先順位付きで列挙する。

### 最優先（本監査で P0 / P1 の原因になっているもの）

1. **色 → 意味の割り当て表**（B-01 / H7）
   1 つの色に 1 つの意味。少なくとも「推奨」「予告（射線・範囲）」「COMBO」「トリガー」「完成ライン」「配置不可」「KEEP」を分離する。
2. **通常ブロック 5 色の識別設計**（B-02 / H-01）
   色相だけでなく明度差・形・記号・質感を含める。COLOR BLAST の読み取りが依存している。
3. **背景・盤面・セル・ブロック・特殊の階層**（B-03 / B-04）
   現状は盤面地 vs 画面地が 1.08、特殊の下地 vs 空セルが 1.24。
4. **HUD の情報階層**（A-01 / A-03 / A-05 / A-04）
   常設する情報、幅配分、CHAIN / COMBO をどこに 1 か所だけ出すか、ステージ名の扱い。
5. **入力フィードバックの定義**（C-01 / C-02）
   成功・失敗・無効のそれぞれに、視覚／音／触覚の 3 チャンネルで何を割り当てるか。
6. **モーダルの定義**（F-02 / F-03 / G-01 / G-05）
   閉じる経路、背景タップ、ボタンの折り返し、暗転の強さ、盤面を見せるかどうか。
7. **VFX の色と強度の段階**（D-02 / D-03）
   通常消去 < COLOR BLAST < 特殊単独 < COMBO の強度差を、量として定義する。

### 次点

8. **文字書体・サイズ・ウェイト・行間**（E-01 / A-08 / E-04）。和文書体の指定を含む。
9. **余白とグリッド**（F-04 / F-06）。縦余白の使い道を決める。
10. **小画面での縮小規則**（F-05 / E-04）。**盤面サイズをステージ内容から独立させる。**
11. **アニメーション時間とイージング**（D-01 / D-04）。同時に出すもの・時間差で出すものを分ける。
12. **SE の役割**（D-08）。現状は未実装なので、何に音を割り当てるかから決める。
13. **画面振動の強度**（未実装）。使う／使わないの判断を含む。
14. **ボタンの通常・押下・無効状態**（G-04）。
15. **objective 表示**（A-06 / A-08）。
16. **CHAIN / COMBO 表示**（A-01 / D-04 / E-03 / H9）。
17. **アクセシビリティ上の最低基準**（H-01〜H-04）。`prefers-reduced-motion`、色以外の手がかり、最小タップ寸法。

## 11. 対象外・未検証

### 本監査の対象外（意図的に見ていない）

- メニュー・ショップ・図鑑・設定・ステージ選択画面（方針文書 第 6 節により第 4 段階）。
- ゲームバランス（閾値・倍率・生成率・ステージ難易度）。
- コアロジックの正しさ（`tests/` の 186 ケースが担当する範囲）。
- DBG パネルの**内部表示内容**そのもの（開発用）。ただし通常画面への影響（F-01）は監査対象に含めた。
- 音・振動・カメラシェイクの**品質**（いずれも未実装のため、有無のみ記録）。

### 未検証（推測していない）

- **初見プレイヤーの理解・注意配分**（第 8 節の仮説 H1〜H10 はすべて未検証）。
- 実機（iOS Safari / Android Chrome）での描画・入力・safe-area・100vh の挙動。
- 実機でのタッチから発光までの総遅延、フレーム落ち。
- 実機での色再現、屋外・低輝度環境での可読性。
- 指・手による遮蔽の実際の量。
- 片手操作での到達性。
- 横画面・タブレット・折りたたみ端末（方針文書は縦 4 幅のみを最低基準としている）。
- 支援技術（スクリーンリーダー等）での利用可否。ARIA が無いことは確認したが、実際の読み上げは未確認。
- 長時間プレイでの疲労・飽き。
- Toon Blast / Block Blast の実物。本文の比較はすべて**方針文書 第 2 節で定義された品質軸との比較**であり、
  実際の画面を確認したものではない。

### 本監査で行っていないこと

- **コード・テスト・ツール・CSS・HTML・依存関係の変更**（差分 0）。
- **UI 修正の実装。**
- **デザインシステムの作成**（第 9 節は「定義すべき項目の列挙」であって定義ではない）。
- **アート制作。**
- 技術基盤の移行提案（方針文書 第 1 節）。
