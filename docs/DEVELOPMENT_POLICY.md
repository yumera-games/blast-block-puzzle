# BLAST BLOCK 開発方針（正式決定）

- **正式決定日**：2026-09-08
- **適用対象**：BLAST BLOCK（`yumera-games/blast-block-puzzle`）
- **適用範囲**：今後の設計・実装・監査・提案のすべて
- **変更手続き**：方針を変えるときは、**実装より先にこの文書を更新して承認を得る**。
  実装を先に変えてから文書を後追いで直すことはしない。

この文書がプロジェクトの一次情報です。他の文書（`CLAUDE.md`、`README.md`）は
要約とリンクだけを持ち、内容が食い違った場合はこの文書を正とします。

## 1. 技術基盤

- **Unity へ移行しない。**
- **Three.js へ移行しない。**
- **現在の Web 基盤（TypeScript / Vite / Phaser）を維持する。**
- 実装は Claude Code で行い、実ブラウザでの検証は Playwright で行う。
- **技術移行そのものを品質改善策として提案しない。**
  「Unity なら演出が良くなる」といった提案はこの方針に反する。
- 現行基盤のまま**製品版品質まで磨く**。

現行基盤では実現不可能な要件が明確になった場合に限り、**具体的な技術的根拠と代替案を
報告する**。報告までが権限であり、**承認前に移行作業へ着手してはならない。**

## 2. 参照作品の扱い

### Toon Blast — 品質水準のベンチマーク

次の観点について、到達すべき品質水準と設計原則を学ぶために参照する。

- 全体の完成度
- UI の情報密度
- 操作への反応
- 破壊時の気持ちよさ
- 演出と音のタイミング
- 報酬の見せ方
- 画面遷移の滑らかさ

**丸写しはしない。** レイアウト・配色・アイコン・演出・キャラクター・素材を
そのまま持ち込まない。参照するのは品質水準と設計原則であり、
表現は BLAST BLOCK 独自のものにする。

### Block Blast — 維持すべき長所

- 盤面が一目で読める
- セルとピースの位置関係が明確
- ドラッグ操作が分かりやすい
- 置ける場所・置けない場所を判断しやすい
- 視覚効果を増やしても盤面認識を阻害しない

**演出を豪華にする場合も、盤面の見やすさと入力の明快さを失ってはならない。**
この 2 つは装飾より優先する。

## 3. 正式な進行順

UI / UX 制作は必ずこの順序で進める。

1. **UI 監査**
2. **デザインシステム定義**
3. **メインプレイ画面 1 枚を製品版品質まで縦切りで完成**
4. **確定したシステムを他画面へ展開**

**順序を飛ばさない。複数段階を同時進行しない。**

2026-09-09 以降、この 4 段階の**前に**パズル版の構想工程が 3 つ入る。
**第 9 節の 6 手順が現在の正式な進行順であり、この節の 4 段階はその手順 4〜6 に対応する。**

## 4. 第 1 段階：UI 監査

**原則としてコードを変更せず**、現状のメインプレイ画面を調査して報告する。

調査項目：

- 情報の優先順位
- 視線の流れ
- 盤面と HUD の比率
- 余白と情報密度
- 色・コントラスト・文字サイズ
- タップ / ドラッグ対象の大きさ
- objective / score / moves / CHAIN / COMBO の理解しやすさ
- モーダルとゲーム画面の関係
- 演出中の盤面視認性
- 操作から反応までの遅延
- 読まれない文章、見落とされる表示、重複した説明、不要な情報
- 勝利・失敗時の感情の山
- SE / VFX / 画面振動の不足・過剰
- 320 / 375 / 393 / 430px での可読性

報告には **問題・原因・優先度・改善方針**を含める。修正の実施は別途承認を得る。

## 5. 第 2 段階：デザインシステム定義

個別画面の装飾を始める前に、BLAST BLOCK 共通のシステムを定義する。

- カラーパレット
- 背景・盤面・セル・ブロックの階層
- 通常ブロックと特殊ブロックの形・色・質感
- 文字書体・サイズ・ウェイト・行間
- HUD の情報階層
- 余白とグリッド
- 角丸 / 枠線 / 影 / ハイライト
- ボタンの通常・押下・無効状態
- モーダル
- objective 表示
- CHAIN / COMBO 表示
- VFX の色と強度
- SE の役割
- 画面振動の強度
- アニメーション時間とイージング
- 小画面での縮小規則
- アクセシビリティ上の最低基準

**画面ごとに異なる装飾を場当たり的に作らない。**

## 6. 第 3 段階（最重要）：メインプレイ画面 1 枚の縦切り

メニュー・ショップ・図鑑・設定などを**同時に直し始めてはならない。**
プレイヤーが最も長く見る実際のゲームプレイ画面を **1 枚だけ**選び、
製品版品質まで完成させる。

完成対象：

盤面 / 上部 HUD / スコア / 残り手数 / 目標表示 / 通常ブロック / 特殊ブロック /
CHAIN 表示 / COMBO 表示 / 予告表示 / トレイ / 操作ボタン / モーダル /
開始・中断・再挑戦 / 勝利演出 / 失敗演出 / タップ反応 / ドラッグ反応 /
合法・不正配置のフィードバック / ブロックの破壊演出 / 特殊起爆 /
スコア加算演出 / 画面振動 / SE・VFX の発生タイミング / 文字階層 / 余白 /
角丸 / 枠線 / 影 / 光 / 質感 / アニメーションの速度と間 /
小画面での可読性・操作性

**これは「UI をきれいにする」工程ではない。** 操作した瞬間の反応、破壊時の
気持ちよさ、情報の理解、音と映像の同期まで含めた UI / UX システムを完成させる工程である。

見た目が完成していても、次のいずれかが残っていれば**第 3 段階は未完了**とする。

- 操作が鈍い
- 何が起きたか分からない
- 盤面が読みにくい
- 演出が弱い、または邪魔
- 音と動きがずれている
- 勝利・失敗の感情が弱い
- 小画面で崩れる
- タップ対象が不明瞭
- 情報の優先順位が曖昧
- **人間プレイで理解・気持ちよさを確認できていない**

## 7. 第 4 段階：他画面への展開条件

メニュー・ショップ・図鑑・設定・ステージ選択などへの展開は、
**第 3 段階が人間評価を含めて承認された後にのみ**開始する。

展開では、第 3 段階で確定した次を再利用する。

色 / 文字 / 余白 / 角丸 / 影 / ボタン / モーダル / アニメーション / 音 /
入力フィードバック / レスポンシブ規則

**他画面の都合で基準を無断変更しない。** 変更が必要ならデザインシステムへ戻り、
整合性を確認してから進める。

## 8. 検証方針

3 種類の検証を**混同しない**。

| 種類 | 確かめられること |
| --- | --- |
| **自動テスト** | ロジックと不変条件 |
| **Playwright** | 実ブラウザ上の表示・操作・回帰 |
| **人間評価** | 理解、読みやすさ、面白さ、気持ちよさ |

**自動テストや Playwright の成功を、人間が理解・満足した証拠として扱ってはならない。**
自動プレイがクリアできたことは「実装が想定どおり動く」ことしか示さない。

最低検証幅：

- 320×568
- 375×667
- 393×852
- 430×932

**静止画だけでは判断できない演出は、連続フレームまたは画面録画も提出する。**

### 端末適応（短い規範）

- **iPhone 15 Pro（393×852 CSS px / DPR 3）を最優先の制作・実機確認基準とする。**
  ただし**その寸法へ固定実装しない。**
- **盤面は常に正方形**とし、**セル寸法は盤面の実寸から計算する。**
- **背景・城・前景・盤面・ブロック・特殊・演出・HUD を分離する。**
  **UI 位置を背景画像へ焼き込まない。**
- **1 枚の完成画面画像を全端末へ表示しない。**背景の引き伸ばし・同色帯での穴埋め・
  横画面で縦画面の左右をぼかして埋めることを禁止する。
- 上の最低検証幅に加え、**縦横両向き**とタブレット・デスクトップも対象とする。

分類ごとの詳細と禁止事項は
[世界観統合ビジュアル試作 8-4 節](./design/CANDY_KINGDOM_VISUAL_INTEGRATION.md)に置く。
**ここでは重複させない。**

**資産（本番人物画像・音素材）の制作順序**

1. **手順 4 で仕様を確定する**
2. 仕様に基づいて資産を制作する
3. 資産の形式・同一性・品質を確認する
4. **手順 5 の縦切り実装へ渡す**

**仕様が未確定のまま人物画像や音素材を制作しない。**
**資産がまだ存在しないことを理由に、仕様そのものを確定不能として扱わない。**

**世界観設計書 10-1 の工程 8「本番 UI・章構成への統合計画」の扱い**：
当面は**手順 4（デザインシステム 2B の計画・確定）**として進める。
**「工程 8 ＝ すでに実装を開始してよい」という意味ではない。**

### 9-3. 維持する基本構造

パズル版でも次は変えない。

- 8×8 盤面
- ピースをドラッグして配置
- 行・列を完成させて消去
- CHAIN / 特殊ブロック / COMBO
- ステージ制
- 短時間でも理解できる明快な操作

これに「**七基の灯を再点火し、失われた王国と最後の王都の名前を回復する**」という固有の目的を加える
（世界観設計書 0-3 の相違 3）。**旧記述の「魔法のお菓子を完成させる」は、旧仮称の時期の目的であり、
経緯として残すが現役の目的としては使わない。**
**色やブロックを別の意匠へ置き換えるだけの着せ替えにしない。**
盤面で行う操作が、**灯の再点火・名前の回復・国の再生・人物の関わり**へつながる構造にする。

**上に挙げた基本構造（8×8 盤面／ドラッグ配置／行・列の消去／CHAIN・特殊ブロック・COMBO／
ステージ制／明快な操作）は、目的の変更によって一切変えない。**

**ゲーム上の通常ブロックの色数を勝手に増やさない。**
ピンク・シルバー・ゴールド・オーロラは UI ／ 特殊 ／ 演出に限って使い、
通常ブロックの識別体系と競合させない。

### 9-4. ビジュアルの位置づけ

- **A2-HW-R（Rainbow Warm Luminous）** — 通常ステージの本命候補。
- **N1（Aurora Black）** — 夜／ボス／高難度／期間限定などの用途候補。
  **通常プレイの本命にする可能性も排除しない。**
  **盤面の騒がしさと長時間プレイへの影響は未判定のまま残す。**

**手順 3 の決定（2026-09-15）：A2-HW-R を採用する。**

- **A2-HW-R**（Rainbow Warm Luminous）— **採用。**通常ステージの基礎案とする。
  根拠は盤面のエッジ量 3.84（画面 4.19 より静か）、色覚 1 型の最小 ΔE 25.91、
  色を落としても盤面の輪郭が残る（1.75）、ゴールド／黄・シアン／青・ピンク／失敗の赤の
  分離が N1 より良いこと、登録済み人物が明るい地からより強く分離すること。
- **N1**（Aurora Black）— **基礎案としては採用しない。**
  ただし N1 が出した**特殊 7.49 ／ COMBO 8.52 ／ セル境界 4.38** は、
  A2-HW-R の 2B を評価するための**性能上の参考値として残す。**
  **N1 の黒地・64 セルの常設シルバー縁・配色を A2-HW-R へ混ぜない。**
  求めるのは、常設の盤面を騒がしくせず特殊・COMBO・勝利の瞬間だけ十分に気づける
  A2-HW-R 側の解決である（2B 草案 3-10）。

決定の全文と根拠は [2B 草案](./design/MAIN_PLAY_DESIGN_SYSTEM_2B.md) 1 節。
